# Поиск по бизнес-сущностям

> `status: active` — написано и покрыто тестами. Не проверено на настоящем потоке: сработает ли
> предохранитель по ключу так, как задумано, покажет только реальный сервис (M-74).

## 1. Суть

Техподдержка не приносит `traceId`. Она приносит `order_id`, `user_id`, номер телефона. Вопрос
звучит как «что вообще происходило с корзиной `12345` за последние сутки» — по всем сервисам и по
всем запросам, а не по одному.

**Трасса на этот вопрос не отвечает и не может.** Заказ создан в одной трассе, фоновый воркер
обработал его через час в другой; общего `trace_id` у них нет и быть не может. Жизненный цикл
сущности — ось, ортогональная трассе (research §Р12).

Разработчик помечает поле ключом сущности — это всё, что от него требуется:

```kotlin
log.info("order created") { field("orderId", id, indexed = true); field("total", sum) }
```

Дальше `get_entity("orderId", "12345", since)` отдаёт хронологию: какие сервисы трогали сущность,
когда, в каких трассах — и оттуда переход в [get_trace](feature-trace-correlation.md).

## 2. Бизнес-ограничения

* Индексируются **только помеченные** поля. Непомеченное поле не найдётся — и это названная цена,
  а не баг: индекс по всем значениям был бы вторым экземпляром логов в виде B-дерева.
* **Ссылка сохраняется, даже если сама запись отброшена семплированием** (research §Р7, пол).
  Без этого фича мертва ровно там, где нужна: «оформилось, но письмо не пришло» — успешный
  сценарий, а успешные трассы живут 1%.
* Ссылка на отброшенную запись отдаётся с признаком: видно «сущность трогали здесь», но тела
  записи нет. Показывать это как полноценную запись нельзя.
* Значение ключа — **недоверенные данные** (research §Р8): в MCP оно проходит тот же скрин, что и
  прочие поля.
* Ограничен не список ключей, а **скорость ссылок**: бюджет на пару (сервис, ключ). Ключ с
  кардинальностью запроса убивает базу в одиночку, поэтому считать надо ссылки, а не ключи
  (research риск 7).
* Ссылки дедуплицируются по `(key, value, trace_id)`: одна сущность в одной трассе — одна ссылка.
* **Подавленный ключ обязан быть виден в выдаче.** Ответ по такому ключу несёт момент
  срабатывания: до него история полная, после — её нет. Молчаливое «ничего не найдено» дало бы
  ложноотрицательный ответ, самый дорогой в расследовании (research §Р15).

## 3. Как это работает

### Схема

```sql
-- словарь ключей: глобальный на инсталляцию, не на сервис
CREATE TABLE entity_key (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

-- партиция ровно та же, что у log_entry
CREATE TABLE entity_ref_20260811 (
    key_id      INTEGER NOT NULL REFERENCES entity_key(id),
    value       TEXT    NOT NULL,
    ts          INTEGER NOT NULL,
    service_id  INTEGER NOT NULL,
    instance_id INTEGER NOT NULL,
    trace_id    BLOB,             -- 16 байт, а не 32-символьный hex
    entry_id    INTEGER           -- rowid в log_entry_20260811; NULL = тело отброшено
);

CREATE INDEX ix_ref_point_20260811
    ON entity_ref_20260811 (key_id, value, ts, service_id, trace_id, entry_id);

CREATE INDEX ix_ref_window_20260811
    ON entity_ref_20260811 (key_id, ts, value);
```

Ключ интернируется, значение — нет: словарь высококардинальных значений стал бы копией таблицы.
Ключ **глобальный**, а не на сервис, иначе главный сценарий разваливается — заказ создал
`orders-api`, обработал воркер, и это обязан быть один `orderId`. Цена — общее пространство имён
ключей на инсталляцию, что согласуется с моделью «одна инсталляция = одна команда» (research §Р11).

### Почему партиции обязаны совпадать с `log_entry`

* **джоин локален:** `entry_id` — rowid в `log_entry` того же месяца, партицию не надо ни угадывать,
  ни обходить `UNION ALL`;
* **ретенция не оставляет висячих ссылок:** одной таблицей `DROP TABLE log_entry_20260710` превращал
  бы часть `entry_id` в мусор, и чинить пришлось бы массовым `UPDATE` по самой большой таблице.
  С совпадающими партициями чинить нечего — читатель знает список живых партиций;
* отсюда же следует, что **ретенция ссылок может быть длиннее ретенции тел**: партиция ссылок
  живёт, когда партиция записей уже удалена, и ссылки честно отдаются без тел.

### Два индекса под две формы запроса

**Точечный** (`ix_ref_point`) — покрывающий, и это совпадает с фазой 1 выдачи MCP не случайно:

```sql
SELECT ts, service_id, trace_id, entry_id
  FROM entity_ref_20260811
 WHERE key_id = ? AND value = ? AND ts BETWEEN ? AND ?
 ORDER BY ts;
```

Все нужные колонки лежат в ключе индекса, `ts` третьей позицией даёт готовый порядок без temp
b-tree — запрос отвечается **целиком из индекса**, к таблице обращения нет. Тела подтягиваются
фазой 2: `LEFT JOIN log_entry_20260811 e ON e.id = r.entry_id`, где `id` — сам rowid, то есть
прямой seek на строку, а не скан. `LEFT` — потому что `entry_id` законно бывает `NULL`.

**Оконный** (`ix_ref_window`) — под агрегацию: с точечным индексом «топ IP за час» шёл бы по всем
значениям ключа с построчной отбраковкой по времени. Здесь окно — непрерывный срез, группировка
сортирует уже внутри него.

Цена второго индекса — примерно утроение стоимости одной ссылки на записи (строка плюс две вставки
в b-дерево), и это прямо кормит риск 7. Поэтому он **не проектное решение, а предмет замера**
(M-35): точечного индекса может хватить и для агрегации, раз высококардинальные ключи всё равно
подавляются предохранителем. Начинать с одного индекса, добавлять второй по результату.

### Дедупликация по трассе

Агент схлопывает ссылки по `(key, value, trace_id)`: одна сущность в одной трассе — **одна**
ссылка, с самым ранним временем и `entry_id` первой сохранённой записи. Пять строк про один заказ
в одном запросе дают одну ссылку, а не пять.

Семантика не страдает: вопрос к `entity_ref` — «трогали ли сущность в этой трассе», а все строки
внутри трассы отдаёт `get_trace`. Объём перестаёт зависеть от того, сколько раз в коде написан
`log.info` про один заказ.

### Предохранитель

Бюджет ссылок в минуту на пару (сервис, ключ). При превышении ключ перестаёт индексироваться
целиком — прореживать ссылки нельзя, это дало бы неполные данные, выглядящие полными.

Устройство — research §Р15: считает и хранит **сервер** (`entity_key_suppressed` в SQLite, то есть
переживает рестарт), исполняет **агент**, узнавая о состоянии из `suppressedKeys` в ответе на
`/ingest`. Снятие — только явным вызовом `POST /api/entities/{key}/unsuppress`: ни минутный
таймер, ни рестарт пода латч не снимают.

## 5. Сценарии

### Сценарий: хронология сущности через несколько трасс *(целевое, ведущий)*
* **Дано:** `orders-api` создал заказ в трассе A, через час воркер обработал его в трассе B; оба
  писали `field("orderId", "12345", indexed = true)`.
* **Когда:** выполняется `get_entity("orderId", "12345", since = -24h)`.
* **Тогда:** возвращаются обе точки в хронологическом порядке с сервисом, временем и своим
  `traceId` у каждой.

### Сценарий: успешный сценарий находится при `sampleRate = 0.01` *(целевое)*
* **Дано:** заказ прошёл без единой ошибки, трасса отброшена семплированием.
* **Когда:** выполняется `get_entity("orderId", "12345")`.
* **Тогда:** ссылка есть, сервис и время видны, `traceId` известен; тело записи помечено как
  несохранённое. **Пустой ответ здесь был бы поломкой фичи**, а не ожидаемым поведением.

### Сценарий: агрегация по значению *(целевое)*
* **Дано:** в `WARN` пишется `field("ip", …, indexed = true)` при неудачной аутентификации.
* **Когда:** запрашивается агрегация по ключу `ip` за сутки.
* **Тогда:** возвращается топ значений со счётчиками.

### Сценарий: предохранитель срабатывает и не сбрасывается сам *(целевое)*
* **Дано:** сервис помечает `requestId`, уникальный на каждый вызов; бюджет ссылок превышен.
* **Когда:** сервер обнаруживает превышение.
* **Тогда:** ключ попадает в `entity_key_suppressed`; следующий ответ на `/ingest` несёт его в
  `suppressedKeys`; агент прекращает эмитировать ссылки по нему. **Ни следующая минута, ни
  рестарт агента, ни рестарт сервера ключ не разблокируют.**

### Сценарий: подавление видно читателю как граница, а не как пустота *(целевое)*
* **Дано:** ключ `ip` подавлен в 14:00.
* **Когда:** выполняется `get_entity("ip", "203.0.113.7", since = -24h)`.
* **Тогда:** возвращаются ссылки **до** 14:00 и признак подавления с моментом срабатывания.
  Ответ «обращений после 14:00 не было» **недопустим** — их наличие неизвестно.

### Сценарий: снятие блокировки *(целевое)*
* **Дано:** причина устранена (пометка снята с кода либо бюджет поднят).
* **Когда:** выполняется `POST /api/entities/{key}/unsuppress`.
* **Тогда:** запись о подавлении удаляется, агенты узнают об этом со следующим батчем.
  Повторный вызов на неподавленном ключе — `200`, не ошибка.

### Сценарий: непомеченное поле не ищется *(целевое, названная граница)*
* **Дано:** `field("total", sum)` без `indexed`.
* **Когда:** запрашивается `get_entity("total", "500")`.
* **Тогда:** ответ — ошибка «ключ не индексируется» со списком индексируемых ключей, а **не**
  пустой результат: пустой результат читается как «такого не было».

## 6. Что не входит в скоуп

* **Автоматическое определение того, что поле — идентификатор.** Эвристика по имени (`*Id`) даст
  и ложные срабатывания, и пропуски; пометка стоит одно слово в вызове.
* **Индекс по всем значениям полей** — дороже самих логов (research §Р5).
* **Аудиторский журнал.** Расследовать здесь можно, системой записи для аудита tracy не является
  (research §Р14).

## 7. Известные особенности

* **Ключ с высокой кардинальностью раздувает `entity_ref`**, потому что ссылки не семплируются
  (research риск 7): `orderId` при 5 заказах/с — ~65 МБ/сутки, `requestId` при 100 rps —
  ~1,3 ГБ/сутки, то есть потолок в 4 ГБ выносится за трое суток. Помечать идентификаторы
  сущностей, а не всё, по чему хочется искать.
* **После рестарта агент один батч шлёт ссылки по подавленному ключу**, пока не получит
  `suppressedKeys` в ответе. Перелёт ограничен одним батчем и считается приемлемым — альтернатива
  (durable-состояние в агенте) означала бы запись на диск внутри чужого пода.
* **Ключи глобальны на инсталляцию.** Два сервиса, пишущие `userId` про разные пространства
  идентификаторов, схлопнутся в один ключ. Это цена за кросс-сервисный поиск, который и есть
  смысл фичи.
* **Ссылка без записи — это данные, а не пустое место.** Ответ обязан различать «сущность не
  встречалась» и «встречалась, тело не сохранено».
* **Значение ключа приходит извне** и потому недоверенное: `get_entity` подчиняется тем же двум
  фазам, что и остальная выдача MCP ([feature-mcp-access](feature-mcp-access.md)).
