# Структурное логирование с разделением доверенного и данных

> `status: draft` — кода нет. Всё ниже описывает **целевое** поведение. Числа, статусы и тексты
> ошибок помечаются проверенными только после того, как появятся в коде.

## 1. Суть

Разработчик пишет строку лога так, что **текст сообщения и данные разделены**: сообщение —
константа, которую написал он сам, значения — именованные поля. tracy забирает и то и другое,
но обращается с ними по-разному: сообщение доверенное, поля — нет.

Разделение делается **в момент записи**, когда происхождение ещё точно известно. Восстановить его
позже, при чтении, невозможно: в строке `"user 42 logged in"` уже не видно, что `42` пришло из
внешнего запроса. Отсюда всё остальное — группировка, поиск, редакция и защита MCP
([feature-mcp-access](feature-mcp-access.md)) — держится на этом одном решении
(research §Р8).

```kotlin
val log = tracyLogger("OrdersRouting")

log.info("user logged in") {
    field("userId", user.id, indexed = true)   // ключ сущности: по нему потом ищут
    field("ip", call.request.origin.remoteHost)
}

log.error("payment provider rejected", cause = e) {
    field("provider", provider.name)
    field("code", response.status.value)
}
```

## 2. Бизнес-ограничения

* Проверка уровня выполняется **до** вычисления аргументов: подавленная запись не должна
  аллоцировать ничего.
* Сообщение — константа в коде. Интерполированное сообщение принимается, но помечается
  `untrusted_message = 1` и дальше обрабатывается как поле, а не как шаблон.
* Редакция выполняется **в агенте, до отправки** (research §Р11). Значение, попавшее под правило,
  не покидает процесс.
* Поле, помеченное `indexed = true`, становится ключом поиска по сущностям
  ([feature-entity-search](feature-entity-search.md)) и **перестаёт семплироваться на уровне
  ссылки**. Помечать идентификаторы сущностей, а не всё подряд: ключ с высокой кардинальностью
  раздувает индекс (research риск 7).
* Агент ведёт **минутные счётчики по шаблонам** и отправляет их всегда, независимо от
  семплирования (research §Р13). Это единственный способ получить честную частоту события.
  Порог уровня на счётчики действует: событие, отключённое порогом, не считается — и это надо
  знать, выставляя порог выше `INFO`.
* Отказ tracy никогда не поднимается в код приложения: ни исключением, ни блокировкой, ни
  занятым потоком. Ошибка отправки видна только в счётчиках самого агента.
* Запись в tracy **не заменяет** вывод в stdout (research §Р10).
* Уровни: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR` — как в `io.github.oshai.kotlinlogging.Level`,
  без своего перечисления.

## 3. Как это работает

1. Вызов `log.info(...) { }` проверяет уровень и, если запись проходит, собирает `LogRecord`.
   Сразу же инкрементируется счётчик `(template, level)` минутного окна. Счётчик освобождён от
   **семплирования**, но не от **порога уровня**: то, что не логировалось вовсе, не считается —
   иначе пришлось бы вычислять шаблон у подавленных вызовов и обещание «подавленная запись не
   стоит ничего» перестало бы выполняться. Для структурного вызова шаблон — это константа-аргумент,
   так что инкремент не трогает лямбду с полями.
2. `trace_id`/`span_id` берутся из `coroutineContext[TracyTraceContext]`, если вызов suspend
   (research §1.3 — иного способа на Kotlin/Native нет).
3. Применяются правила редакции по именам полей и по регулярным выражениям.
4. Запись кладётся в кольцевой буфер (лимит в **байтах**, не в записях).
5. Батчер отдаёт накопленное отправителю раз в `flushInterval` или по `maxBatchBytes`;
   запись уровня `ERROR` вызывает flush синхронно (research риск 2).
6. Параллельно запись уходит в исходный аппендер — stdout остаётся нетронутым.

Перехват чужого логирования настраивается по-разному на платформах (research §Р3):

| | native | JVM |
|---|---|---|
| Как встраиваемся | `KotlinLoggingConfiguration.direct.appender = TracyAppender` | SLF4J-аппендер |
| Что ловим | всё, что идёт через kotlin-logging | всё, что идёт через SLF4J, включая логи библиотек |
| Что **не** ловим | `println`, внутренний логгер Ktor (гипотеза, проверить в M2) | `println` |

## 5. Сценарии

### Сценарий: структурная запись доезжает до сервера с разделёнными полями *(целевое)*
* **Дано:** агент настроен, сервер доступен.
* **Когда:** сервис вызывает `log.info("user logged in") { field("userId", 42) }`.
* **Тогда:** сервер сохраняет запись с `message = "user logged in"`, `untrusted_message = 0`,
  `fields = {"userId": 42}`.

### Сценарий: интерполированное сообщение помечается недоверенным *(целевое)*
* **Дано:** то же.
* **Когда:** сервис вызывает `log.info("user $id logged in")`.
* **Тогда:** запись сохраняется с `untrusted_message = 1`; шаблон вычисляется маскированием
  (research §Р8) и кладётся в `log_template`, но доверия не даёт.

### Сценарий: подавленный уровень ничего не стоит *(целевое)*
* **Дано:** порог агента — `INFO`.
* **Когда:** вызывается `log.debug("…") { field("payload", heavyToString()) }`.
* **Тогда:** `heavyToString()` **не вызывается**, аллокаций нет.

### Сценарий: сервер недоступен — сервис работает *(целевое)*
* **Дано:** `TRACY_ENDPOINT` указывает в никуда.
* **Когда:** сервис обслуживает запросы и пишет логи.
* **Тогда:** запросы обслуживаются штатно; записи копятся в буфере, при переполнении дропаются
  с конца, счётчик дропов растёт; исключений в код приложения не приходит.

### Сценарий: секрет не покидает процесс *(целевое)*
* **Дано:** дефолтные правила редакции.
* **Когда:** пишется `field("authorization", "Bearer eyJ…")`.
* **Тогда:** на провод уходит `"authorization": "***"`; полное значение в тело запроса не попадает.

## 6. Что не входит в скоуп

* **Перехват stdout** — противоречит §Р10 и ломает вывод, который собирает кластер.
* **Своя иерархия логгеров, фильтры по пакетам, конфиг-файлы** — уровень задаётся глобально и
  переопределяется на логгер; всё остальное остаётся за штатным логированием приложения.
* **Автоматическое определение файла и строки** — на Kotlin/Native дешёвого способа нет;
  якорем служит имя логгера.

## 7. Известные особенности

* **Разделение доверенного и данных нельзя добавить потом.** Оно должно быть в модели `:shared` с
  первого коммита: иначе переписывать придётся агент, схему БД и MCP разом (research §4).
* **На JVM подменять `KotlinLoggingConfiguration.loggerFactory` нельзя** — это отключит SLF4J для
  всего приложения (research §1.4, следствие 2). Библиотека, которая так делает, ломает хост-сервис
  молча.
* **`Appender.log` не suspend** и trace id в себе не несёт — корреляция для перехваченных чужих
  логов доступна только там, где её удаётся достать иначе (research §1.3).
