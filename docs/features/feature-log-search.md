# Поиск, группировка и ретенция

> `status: active` — написано и покрыто тестами. Полнотекстовый поиск дописан в M7: до него
> FTS-индекс заполнялся на каждом приёме и не читался никем, то есть решение Р5 было построено
> наполовину. Открыт M-52 — доля записей в топ-100 шаблонов проверяется на настоящем потоке.

## 1. Суть

Хранилище tracy — **один файл SQLite** в нативном бинаре. Полнотекстовый поиск даёт FTS5, который
в sqlx4k уже собран (research §1.1 — проверено по `libsqlx4k_sqlite.a`: SQLite 3.46.0,
`SQLITE_ENABLE_FTS5`, токенайзер `trigram`, `contentless_delete`). Внешнего поискового движка нет,
второго процесса нет.

Три операции чтения, ради которых всё построено:

| Операция | Ответ на вопрос |
|---|---|
| Поиск по тексту и фильтрам | «где вообще упоминается `NoTransformationFound`» |
| Окно времени по всем сервисам | «что происходило в кластере с 14:02 по 14:04» |
| Частота шаблонов во времени | «как часто за час падал парсинг конфига и участилось ли это» |
| Восстановление цепочки по `traceId` | «что произошло по этому запросу и где ушло время» — [feature-trace-correlation](feature-trace-correlation.md) |
| Хронология сущности | «что было с корзиной 12345» — [feature-entity-search](feature-entity-search.md) |

## 2. Бизнес-ограничения

* Каждый запрос чтения имеет **жёсткий потолок** выдачи; при усечении ответ явно сообщает,
  сколько записей осталось за кадром. Молча обрезанная выдача читается как «это всё» и врёт.
* FTS5 строится **над таблицей шаблонов**, а не над записями (research §Р5). Поиск двухшаговый:
  найти шаблоны полнотекстом → взять записи по `(template_id, ts)`.
* **Поиск по подставленному значению через FTS не работает** и работать не будет: в индексе лежит
  `order <num> not found`, а не `order 8123 not found`. Для значений есть
  [feature-entity-search](feature-entity-search.md).
* Значения полей полнотекстово не индексируются: индекс `trigram` по телам запросов занял бы
  больше места, чем сами логи.
* Класс исключения — **точное совпадение** по интернированной колонке, не полнотекст. Стектрейс
  не индексируется вовсе.
* Ретенция ограничена **и по времени, и по размеру файла**. Потолок размера — жёсткий.
* Удаление старого — `DROP TABLE` суточной партиции, не `DELETE`: большой `DELETE` в SQLite
  оставляет фрагментацию и требует `VACUUM`.
* «Нет данных» отображается как «нет данных», никогда как ноль.

## 3. Как это работает

Схема (детали и миграции — [tracy-server](../services/tracy-server.md); образец механики миграций —
`katcher/server/src/commonMain/kotlin/ru/workinprogress/katcher/db/Migrate.kt`):

| Таблица | Назначение |
|---|---|
| `log_entry_YYYYMMDD` | записи; **суточная** партиция, чтобы и ретенция, и вытеснение были `DROP TABLE` |
| `span_YYYYMMDD` | спаны: `trace_id, span_id, parent_span_id, kind, name, ts, duration_ms, status, error, fields`; та же нарезка |
| `log_template` | текст шаблона; **сообщение хранится здесь, а не в каждой записи**. Инвариант: сюда не попадает ничего, не прошедшее редакцию (research §1.10) |
| `template_count` | `(service_id, template_id, level, release, minute, count)` — счётчики от агента, **точные при любом семплировании** (research §Р13) |
| `entity_ref_YYYYMMDD` | ссылки на сущности — [feature-entity-search](feature-entity-search.md) |
| `template_fts` | FTS5 над `log_template.text`, `contentless_delete`, токенайзер `trigram` |
| `service`, `instance`, `exception_class` | справочники, заводятся сами по первому батчу |

Индексы: по записям — `(trace_id)`, `(template_id, ts)`, `(service_id, level, ts)`,
`(exception_class_id, ts)`; по спанам — `(trace_id)`, `(trace_id, parent_span_id)` для сборки
дерева и `(service_id, name, duration_ms)` для поиска медленных; по ссылкам — два, DDL в
[feature-entity-search](feature-entity-search.md).

**Отдельного индекса по `(ts)` нет.** При суточных партициях партиция и есть фильтр по времени, а
внутри неё порядок вставки совпадает с порядком времени — запрос по окну обслуживается выбором
партиции и сканом в порядке rowid. Индекс здесь был бы платой ни за что.

Спаны прибавляют к объёму немного: один-два на запрос против двух-трёх записей лога, и они
короткие. Под ту же ретенцию и то же семплирование они попадают целиком — с одним исключением:
**спан входящего запроса сохраняется всегда** (research §Р7), поэтому его объём считается по
полному потоку запросов, а не по семплированному.

**Арифметика, которая определяет всё остальное.** Сервис на 100 rps с двумя строками на запрос —
17,3 млн записей и ≈ 5 ГБ в сутки на один сервис. Без семплирования (research §Р7) обещание «один
файл SQLite» неправда. С ним и с решениями Р5/Р6 — **≈ 145 МБ в сутки суммарно**, то есть месяц
истории в ≈ 4,3 ГБ: тела 56 МБ, ссылки на сущности 65 МБ, спаны 18 МБ, счётчики 6 МБ, FTS почти
ноль. Разбивка и то, как она менялась, — research §Р6.

Из разбивки следует неочевидное: **ссылки на сущности стоят дороже самих тел записей.** Отсюда и
предохранитель (research §Р15), и правило помечать идентификаторы сущностей, а не всё подряд.

Группировка по шаблону: структурная запись даёт шаблон бесплатно (`message` и есть шаблон,
[feature-structured-logging](feature-structured-logging.md)); интерполированная — через маскирование
переменных частей (числа, UUID, hex, кавычки, пути). Маскирование даёт **группировку**, но не
доверие: такое сообщение остаётся `untrusted_message = 1`.

**Частота считается по счётчикам агента, а не по сохранённым записям** (research §Р13). Агент
шлёт `(template, level, count)` за минутное окно всегда, независимо от семплирования, поэтому
`/api/templates` отдаёт точные числа и ряд по времени. Считать частоту по строкам в базе было бы
занижением в `1/sampleRate` раз — и, что хуже, без всякого признака этого в ответе.

**Что честно означает «окно времени».** Запрос за 14:02–14:04 без фильтра по сервису возвращает:
**все** записи `WARN` и выше, ссылки на сущности, точные счётчики по шаблонам — и `sampleRate`
долю тел уровня `INFO` вместе со спанами их трасс. Это рабочий ответ для «покажи, что происходило,
я сам найду странное», но это **не** «все логи». Формулировка «покажи вообще всё» в отношении
tracy неверна, и API не должен её подразумевать.

Спаны в поле семплирования больше не входят (research §Р7): «сколько всего было запросов в этом
окне» — вопрос к metrik, где счётчики точные и стоят на два порядка дешевле.

## 5. Сценарии

### Сценарий: поиск по подстроке находит запись *(целевое)*
* **Дано:** в базе есть запись с `message`, содержащим `NoTransformationFoundException`.
* **Когда:** выполняется поиск по подстроке `TransformationFound`.
* **Тогда:** запись возвращается; план запроса использует индекс FTS5, а не полный скан.

### Сценарий: выдача усечена и говорит об этом *(целевое)*
* **Дано:** под фильтр подходит 12 000 записей, потолок — 200.
* **Когда:** выполняется поиск.
* **Тогда:** возвращаются 200 записей и признак усечения с числом оставшихся.

### Сценарий: превышение потолка размера вытесняет старейшие сутки *(целевое)*
* **Дано:** `TRACY_DB_MAX_BYTES` достигнут.
* **Когда:** приходит новый батч.
* **Тогда:** батч записывается; старейшие сутки удалены целиком; факт вытеснения виден в
  `/api/health` и в счётчиках.

### Сценарий: одинаковые по смыслу строки группируются *(целевое, гипотеза research §Р8)*
* **Дано:** 40 000 записей `"order 8123 not found"` с разными номерами.
* **Когда:** запрашивается группировка по шаблону.
* **Тогда:** это одна группа `"order <num> not found"` со счётчиком 40 000.
* **Проверка гипотезы:** доля записей, попавших в 100 самых частых шаблонов, на реальном потоке.
  Ниже 60% — подход не работает, группировка строится иначе (M5).

## 6. Что не входит в скоуп

* **Свой язык запросов** (аналог LogQL). Фильтры — параметрами: сервис, инстанс, уровень, диапазон
  времени, подстрока, `trace_id`, ключ и значение сущности. Язык запросов пришлось бы объяснять и
  агенту, и человеку.
* **Алерты по логам** — их место в metrik, где уже есть правила и доставка. Счётчики Р13 делают
  их технически возможными здесь, и именно поэтому границу надо держать явно: второе место, куда
  надо смотреть, хуже отсутствующей функции.
* **Live tail.** Живой поток одного сервиса — это `kubectl logs -f`, и он покрывает случай лучше,
  чем что-либо поверх батчей, SQLite и FTS5 (research §Р10). Осмысленная форма для tracy — тейл
  **нескольких сервисов по одной трассе**, чего `kubectl` не умеет; отложено в M-96, дверь открыта
  (`ktor-server-sse` под native опубликован).
* **Аудиторский журнал.** Расследовать можно, системой записи для аудита tracy не является:
  против этого работают семплирование, ретенция, вытеснение по размеру и редакция
  (research §Р14).
* **Долгая архивная ретенция и выгрузка в S3** — за пределами обещания «один файл».

## 7. Известные особенности

* **Запись в FTS5 перестала быть горячей**: индекс строится над шаблонами, то есть трогается
  только при появлении **нового** шаблона, а не на каждую запись (research §Р5). Риск 5 в
  исходной формулировке («вставка дорожает из-за `trigram`») этим снят — но проверить бенчмарком
  всё равно надо, в M-35.
* **`PRAGMA synchronous = NORMAL`** при WAL: для логов правильный размен — теряется в худшем
  случае последний коммит, а пропускная способность записи отличается кратно.
* **Запрос за месяц идёт `UNION ALL` по тридцати партициям.** Это цена за константную ретенцию;
  узкое окно задевает одну-две.
* **`contentless_delete` требует SQLite ≥ 3.43** — в sqlx4k 1.13.0 версия 3.46.0, условие
  выполняется. При понижении версии sqlx4k проверять заново.
* **Помесячные партиции означают, что запрос за диапазон может задевать две таблицы** — это
  осознанная цена за `DROP TABLE` вместо `VACUUM`.
