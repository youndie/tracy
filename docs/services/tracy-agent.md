# tracy-agent

> `status: active` — написан. Одна оговорка, найденная при подготовке M7 и стоящая того, чтобы
> её прочли: цикла доставки до M7 **не существовало** — `Sender` умел отправить один батч,
> `flushInterval` не читал ни один код. Теперь доставку ведёт `TracyDelivery`. Ни один настоящий
> сервис к агенту пока не подключён (M-74).

## 1. Зона ответственности

Живёт **внутри чужого процесса**. Даёт API структурного логирования и `withSpan`, читает и создаёт
`traceparent`, открывает спаны на границах (входящий запрос, исходящий HTTP-вызов), буферизует,
семплирует, редактирует и отправляет всё это на сервер.

Чем **не** занимается: не хранит, не ищет, не показывает, не перехватывает stdout, не отключает
существующее логирование приложения и **не инструментирует библиотеки автоматически** — драйверы
БД, кэши и очереди оборачиваются вручную через `withSpan` или не оборачиваются вовсе
(research §Р1).

> **Главный инвариант: отказ tracy не влияет на целевой сервис.** Ни исключением, ни блокировкой,
> ни отобранным потоком, ни неограниченным ростом памяти. Всё, что агент умеет делать при
> проблеме, — считать счётчик и дропать записи.

Инвариант не декларативный: metrik уже дважды молчал в проде месяцами именно потому, что
компонент такого рода обязан глотать свои ошибки (research §1.5). Поэтому у агента должны быть
тест против настоящего сокета и способ спросить «доехало ли», возвращающий факт, а не намерение.

## 2. Контракт

[protocol-ingest](../api/protocol-ingest.md). Модель записи и разбор `traceparent` — в `:shared`
(`ru.workinprogress.tracy.wire`), общие для агента и сервера. Поля здесь не дублируются.

## 3. Как устроено

Подключение — как metrik, одной установкой плагина; роуты инструментировать не надо:

```kotlin
install(Tracy) {
    service = "orders-api"
    apiKey = System.getenv("TRACY_INGEST_KEY")
    endpoint = System.getenv("TRACY_ENDPOINT")
    release = System.getenv("RELEASE")
    instanceId = System.getenv("POD_NAME")
    sampleRate = 0.01
    slowThreshold = 1.seconds
    // Правила по именам полей И по тексту сообщения: в настоящих логах секрет приезжает
    // внутри URL, где имени поля нет вовсе (research §1.10).
    redact { field("authorization"); field("cookie"); urls(); regex("""(?i)bearer\s+\S+""") }
}
```

Спаны на границах ставятся этим же плагином и плагином клиента — руками ничего размечать не надо.
Ручная разметка нужна только внутри сервиса:

```kotlin
withSpan("persistOrder") { orders.save(order) }
```

Три вещи, которые не видны из одного файла:

**Точка перехвата разная на платформах** (research §Р3). На нативе — подмена
`KotlinLoggingConfiguration.direct.appender`; на JVM — SLF4J-аппендер, потому что подмена фабрики
kotlin-logging снесла бы логбэк-конфиг приложения и логи библиотек.

**Корреляция берётся только из корутинного контекста** (research §1.3). `ThreadContextElement`
на Kotlin/Native не существует, MDC — тоже; значит `trace_id` доступен там, где вызов suspend,
и недоступен в глубине не-suspend стека. Это ограничение платформы, а не недоделка.

**Решение о сохранении принимается в конце запроса, но вниз по цепочке не распространяется**
(research §Р7). Записи копятся, и на завершении сохраняются целиком, если был `WARN`/`ERROR` или
5xx, либо превышен `slowThreshold`, либо во входящем `traceparent` уже стоял `sampled`, либо
запрос помечен `X-Tracy-Force`; иначе — с вероятностью `sampleRate`. Пол: `WARN` и выше **и спан
входящего запроса** сохраняются всегда.

Исходящим вызовам передаётся только **головное** решение (унаследованный или принудительный
`sampled`): к моменту хвостового решения вызовы уже сделаны, и заголовок задним числом не
меняется. Для ошибок этого хватает — они поднимаются вверх ответами, и каждый сервис приходит к
нужному решению сам.

## 4. Зависимости

| Тип | Имя | Для чего |
|---|---|---|
| Service | tracy-server | приём батчей |
| Library | `ktor-client-curl` (native) / `ktor-client-cio` (jvm) | отправка; на нативе CIO не умеет TLS и тянет `SelectorManager` |
| Library | `io.github.oshai:kotlin-logging` 8.0.4 | фасад и точка перехвата на нативе |
| Library | `ktor-server-call-id` | чтение/генерация идентификатора запроса; под native опубликован |

## 5. Конфигурация

| Параметр | Дефолт | Смысл |
|---|---|---|
| `service` | — | обязателен; логическое имя сервиса |
| `apiKey` | — | обязателен; ingest-key инсталляции |
| `endpoint` | — | обязателен; базовый URL tracy-server |
| `instanceId` | `$HOSTNAME` | **задавать явно из имени пода**, если `HOSTNAME` в чарте переопределён |
| `release` | нет | версия релиза |
| `level` | `INFO` | порог. **Первый и самый сильный рычаг объёма**: на настоящих логах `TRACE`/`DEBUG` — это 90% байт (research §1.10), и они отсекаются до всякого семплирования |
| `sampleRate` | `0.01` | доля успешных и быстрых трасс, сохраняемых целиком |
| `slowThreshold` | `1s` | запрос дольше — сохраняется целиком независимо от `sampleRate` |
| `spans` | `true` | пограничные спаны; выключение оставляет только логи с `trace_id` |
| `entityRefsPerMinute` | `2000` | подсказка агенту, сколько ссылок на ключ он ждёт; настоящий бюджет и предохранитель — на сервере (research §Р15) |
| `flushInterval` | `1s` | периодичность батча |
| `maxBufferBytes` | `8 MiB` | потолок буфера **в байтах** |
| `maxBatchBytes` | `1 MiB` | потолок одного батча |

Пустые обязательные значения должны валить старт приложения намеренно — как в metrik. Агент,
молча выключившийся из-за опечатки в переменной, неотличим от исправного (research §1.5).

## 6. Инфраструктура и деплой

Библиотека, не сервис: публикуется в Maven, деплоя своего не имеет. В целевом образе нужны
`ca-certificates`, если endpoint по https (research §1.5, metrik §1.7).

## 7. Локальный запуск

```bash
./gradlew :agent:jvmTest
./gradlew :agent:macosArm64Test
```

Для сквозной проверки нужен поднятый `:server` — см. [tracy-server](tracy-server.md) §7.

## 8. Сознательные ограничения / грабли

* **Не перехватывает stdout** — намеренно (research §Р10): stdout остаётся страховкой на случай
  падения процесса и недоступности сервера.
* **`println` и внутренний логгер Ktor на нативе не ловятся** (гипотеза, проверить в M2) — это
  граница, которую надо написать в README, а не подразумевать.
* **`SelectorManager` нельзя вешать на `Dispatchers.Default`**: один селектор в чужом процессе —
  это отобранный у сервиса воркер, а два на двухъядерном поде ломают `delay` во всём процессе
  (research §Р4).
* **Доменное имя на Kotlin/Native не резолвится** — резолвить самим, на каждое подключение
  (research §1.5).
* **Буфер теряется при `SIGKILL`** — записи перед падением, то есть самые нужные, не уедут.
  Смягчение: синхронный flush на `ERROR` плюс stdout (research риск 2).
* **Редакция по форме ловит известные формы.** Собственный формат ключа, не похожий ни на что из
  таблицы правил, проедет. Это последний рубеж, а не разрешение логировать секреты — и найденный
  в настоящих логах токен приехал именно от библиотеки, а не от прикладного кода
  (research §1.10).
* **Спанов на операции БД и кэша нет** — только границы и ручной `withSpan` (research §Р1).
  Неинструментованное время видно как `unattributedMs` у родителя, а не теряется.
* **`withSpan` в не-suspend коде не найдёт родителя** — та же причина, что и у `trace_id`
  (research §1.3).
* **Агент не решает, какой ключ подавить, — он исполняет.** Состояние живёт на сервере, потому что
  у агента нет durable-хранилища, а инстансов много: каждый принимал бы решение отдельно и по
  своему бюджету. Обратная сторона — после рестарта один батч ссылок по подавленному ключу уедет,
  пока не придёт `suppressedKeys` (research §Р15).
