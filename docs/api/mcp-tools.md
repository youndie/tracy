# API: MCP-инструменты

> `status: draft` — кода нет. Транспорт и авторизация целиком повторяют katcher, где это работает
> в проде (research §1.8); новое здесь — состав инструментов и двухфазная выдача применительно
> к логам.

Транспорт — `mcpStatelessStreamableHttp` на Ktor CIO, эндпоинт `POST /mcp`. Read-only инструментам
сессия не нужна, поэтому stateless.

```bash
claude mcp add --transport http tracy https://tracy.example/mcp \
  --header "Authorization: Bearer $TRACY_MCP_TOKEN"
```

## Инструменты

| Инструмент | Аннотации | Что отдаёт |
|---|---|---|
| `list_services` | `readOnly` | сервисы, инстансы, последняя активность, произведено и сохранено байт по уровням |
| `search_logs(service?, instance?, level?, since?, until?, query?, templateId?, exceptionClass?, entityKey?, entityValue?, limit)` | `readOnly` | **структура** записей: время, сервис, уровень, логгер, шаблон, `traceId`, ключи полей |
| `get_trace(traceId, limit, depth?)` | `readOnly` | **дерево спанов с длительностями + вписанные записи логов** по всем сервисам |
| `get_entity(key, value, since?, until?, limit)` | `readOnly` | **хронология бизнес-сущности** через все сервисы и трассы |
| `search_spans(service?, name?, minDurationMs?, status?, since, until, limit)` | `readOnly` | вход без `traceId`: «какие запросы были медленными» |
| `top_templates(service?, since, until?, level?, release?, step?, limit)` | `readOnly` | частотные шаблоны со **точными** счётчиками; `step` даёт ряд по времени, `release` — разрез по выкату |
| `get_entry_content(entryIds, checked)` | `readOnly` | **значения полей и свободный текст** — только после отчёта, см. «Две фазы» |

Семь инструментов — в рекомендованном коридоре 1–10; модели деградируют после 30–40 (katcher §5).

**Входов четыре, и агент должен выбирать между ними осознанно:**

| Что на руках | Инструмент |
|---|---|
| `traceId` — из отчёта katcher, из ответа сервиса, из заголовка | `get_trace` |
| `orderId`, `userId`, номер телефона — то, с чем приходит техподдержка | `get_entity` |
| «было медленно», сервис и примерное время | `search_spans` |
| окно времени и аномалия на графике | `top_templates`, затем `search_logs` |
| «как часто это происходит» / «после какого выката» | `top_templates` со `step` и `release` |

Все они сходятся в `traceId` и дальше в `get_trace` — это и есть форма расследования: найти
трассу тем ключом, который есть, и раскрыть её.

**Курсора в выдаче намеренно нет.** При усечении агент получает число оставшихся и подсказку,
каким фильтром сузить, но не способ листать дальше. Листание сжигает контекст ради тех же данных;
сужение приводит к ответу. Это решение, а не пробел.

Различие между первыми двумя — не удобство, а разные оси данных: жизненный цикл сущности
разорван между трассами (заказ создан в одной, воркер обработал через час в другой), и `get_trace`
на него не отвечает **принципиально** (research §Р12). Описания инструментов обязаны говорить это
прямо, иначе агент будет начинать с `search_logs` там, где есть точный ключ.

**Точность выдачи различается, и это часть контракта:**

* `top_templates` — **точные** числа: считаны агентом до семплирования (research §Р13). Их можно
  сравнивать между окнами и умножать.
* `search_logs` по окну — **выборка**: спаны всех запросов, весь `WARN+`, ссылки на сущности и
  `sampleRate` доля тел `INFO`. Ответ несёт `sampleRate` явным полем.
* `get_entity` — ссылки **полные**, тела выборочные: `entryId: null` означает «трогали, тело не
  сохранено», а не «не было». Если по ключу сработал предохранитель, ответ несёт `suppressedSince`,
  и **выдача за этим моментом ничего не утверждает**: агент обязан читать это как «неизвестно»,
  а не как «не было». Описание инструмента говорит это прямым текстом — модель, не предупреждённая
  о границе, выведет из пустоты отрицательный факт.

### Форма ответа `get_trace`

Дерево, а не плоский список: узел — спан (сервис, имя, длительность, статус), у него дети-спаны и
записи логов, сделанные внутри него. Плюс вычисляемые поля, которые отвечают на вопрос «где
время» и «чего не хватает»:

| Поле | Зачем агенту |
|---|---|
| `unattributedMs` | время родителя за вычетом известных детей — «здесь что-то есть, но оно не инструментовано» |
| `noRemoteData` | вызов был, ответной стороны нет: **потерянное звено**, а не отсутствие вызова |
| `unterminated` | спан не закрыт — сброшен при штатном завершении процесса |
| `orphan` | родитель не доехал; узел подвешен к корню |

Различие между «звена нет» и «звено потеряно» здесь принципиально: без него агент делает вывод
«сервис не участвовал» из того, что на самом деле означает «данных не сохранилось».

`depth` ограничивает глубину дерева, `limit` — число записей логов; спаны при усечении логов
остаются все, потому что именно они держат форму цепочки.

## Бюджет контекста — часть контракта

Инструмент, способный вернуть 5 000 строк, бесполезен: он тратит контекст, ради которого агента и
позвали. Поэтому:

* у каждого инструмента серверный максимум `limit`, и он **ниже**, чем у HTTP-API;
* усечение возвращается явно: `truncated`, `remaining` и подсказка, каким фильтром сузить;
* `search_logs` по умолчанию отдаёт **шаблоны, а не тела**: чтобы понять «что происходит»,
  тысяча вариаций одной строки не нужна;
* `top_templates` существует именно для того, чтобы первый вопрос агента не был «дай мне все
  логи»;
* `top_templates` отдаёт `templateId`, а `search_logs` его принимает — **переход от «что ломается
  чаще всего» к «покажи конкретные случаи» прямой**, без поиска текстом по собственной же выдаче;
* `query` ищет по **шаблонам**, а не по телам записей (research §Р5): подставленное значение через
  него не найдётся, для значений есть `get_entity`. Класс исключения — отдельный параметр с точным
  совпадением, а не подстрока.

## Две фазы

Порядок принципиален: агента, уже прочитавшего инъекцию, бессмысленно спрашивать, инъекция ли это.

**Фаза 1** (`search_logs`, `get_trace`, `top_templates`) — только то, через что нельзя пронести
прозу: время, идентификаторы, уровни, имена логгеров, шаблоны разработчика, **ключи** полей и типы
значений. Каждый токен профильтрован до идентификаторных символов.

**Фаза 2** (`get_entry_content`) — значения и свободный текст. Требует параметра `checked`:
опровержимого отчёта о том, что агент проверил структуру из фазы 1 (какие записи, какого сервиса,
какой трассы). Опровержимого — сервер знает настоящие данные и отказывает, если отчёт с ними не
сходится: записи не из этой выборки, несуществующие `entryId`, пустой отчёт.

**Ловушка, оплаченная katcher, и её здесь надо избежать.** Первая версия гейта katcher требовала,
чтобы **все** заявленные фреймы резолвились в репозитории, — и блокировала агента, честно
пометившего библиотечные фреймы, пропуская того, кто отчитался скупее: правило поощряло менее
аккуратный отчёт. Для tracy отчёт должен требовать **достаточного**, а не полного: одна запись,
сошедшаяся с выборкой, — и содержимое отдаётся.

## Скрин недоверенного

Применяется к значениям полей и к сообщениям с `untrusted_message = 1` — **не** к шаблонам,
написанным разработчиком (research §Р8, риск 4). Правила — как в katcher `CrashTrust`: язык,
обращённый к читателю; shell-вызовы; упоминания секретов; невидимые символы; проза, выдающая себя
за структуру.

При срабатывании:

* значение **не отдаётся вовсе**, возвращаются только сработавшие правила;
* находки **никогда не цитируют** удержанный текст — их читает тот самый агент, которого
  защищаем;
* сама запись остаётся видна с `withheld: true`. Тихо выкидывать её было бы хуже: подозрительная
  запись исчезла бы из поля зрения.

Композиция односторонняя: отчёт агента умеет только **ужесточать**. Ничто не разблокирует то, что
отверг статический скрин.

## Авторизация и транспорт

| | Как |
|---|---|
| Токен | статический bearer в `TRACY_MCP_TOKEN`, сравнение constant-time |
| Выключено по умолчанию | нет токена — нет ни транспорта, ни перехватчика, ни ingress-маршрута |
| `Host` | `TRACY_MCP_ALLOWED_HOSTS`; по умолчанию SDK разрешает только localhost |
| Прокси | отдельный ingress-маршрут мимо forward-auth middleware, создаётся только при заданном токене |
| Не переиспользуем | доверие к `X-Auth-Request-*` — оно принимает любую заявленную личность |

**Известный гап:** OAuth 2.1 из спеки (RFC 9728, RFC 8707) не реализован. Для single-tenant
self-hosted статический токен — прагматичный выбор, но это отклонение от спеки, а не соответствие
ей. Ротации токена нет: правка секрета и передеплой.

## Грабли SDK 0.15.0 (проверены в katcher)

* Типы живут в `io.modelcontextprotocol.kotlin.sdk.types`, а не `…sdk`. **Примеры на сайте не
  компилируются**; сигнатуры смотреть в klib (`default/linkdata/`) или в dokka.
* `addTool`: параметр называется `toolAnnotations` (не `annotations`), схема — `ToolSchema`
  (не `Tool.Input`), хендлер — `suspend ClientConnection.(CallToolRequest) -> CallToolResult`.
* `mcpStatelessStreamableHttp` — расширение `Application`, не `Route`; сам ставит роутинг, внутрь
  `authenticate { }` не вкладывается.
* **`protocolVersion` пропадает из ответа**, когда согласованная версия совпадает с дефолтом
  `InitializeResult`: kotlinx.serialization не пишет дефолты. Ломается любой актуальный клиент.
  Обход — подменять версию **в запросе** на `2025-06-18`. Шим временный, убрать при исправлении
  в SDK.
