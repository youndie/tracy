# protocol-ingest — провод между агентом и сервером

> `status: active` — провод написан, обе стороны его говорят, прогнан на живом контейнере.
> Одно поле добавилось по факту M7: ответ несёт `malformed` — число нераспознанных строк. Оно
> считалось декодером с самого начала «чтобы у агента был повод заметить», и до M7 не покидало
> сервер; вдобавок `accepted` со значением 0 опускался сериализатором, и батч, отвергнутый
> целиком, отвечал `{}` — байт в байт как успех. Поля ниже фиксируют замысел; при расхождении с кодом
> правится **этот** документ.

Транспорт: **HTTP POST**, `Content-Type: application/x-ndjson`. Одна строка тела = один элемент:
запись лога, спан, счётчик шаблона или ссылка на сущность. Обоснование выбора (почему не UDP, как в metrik) —
[research](../research/research-architecture.md) §Р2.

```
POST /ingest HTTP/1.1
Content-Type: application/x-ndjson
X-Tracy-Key: tr_live_9f3a…
X-Tracy-Service: orders-api
X-Tracy-Instance: orders-api-7d9f8-x2k1
X-Tracy-Release: 1.4.212
X-Tracy-Seq: 4218

{"t":1754049600123,"l":"INFO","g":"OrdersRouting","m":"user logged in",…}
{"k":"s","sp":"00f067aa0ba902b7","tr":"4bf92f…4736","nm":"POST /orders","t":1754049600120,"d":412,…}
{"t":1754049600131,"l":"ERROR","g":"OrdersRouting","m":"payment provider rejected",…}
```

Все четыре вида идут **в одном потоке** намеренно: спан и записи, которые он охватывает,
принимаются одной транзакцией, и промежуточного состояния «спан есть, логов нет» не бывает.
Различает их поле `k`; его отсутствие означает запись лога — самый частый случай не платит
за дискриминатор.

## Инварианты

1. **Ответ означает записанное.** `202` отдаётся только после того, как батч лёг в БД. Иначе
   агент выбросит записи, которых нигде нет.
2. **Батч идемпотентен** по `(instance, seq)`: повторная доставка после таймаута не должна
   удваивать записи.
3. **Агент никогда не блокирует хост-сервис.** Ни ошибка, ни недоступность сервера, ни
   переполнение буфера не поднимаются в код приложения.
4. **Переполнение видно.** Дропнутые записи считаются и отправляются счётчиком в следующем батче —
   молчаливая потеря в системе наблюдаемости недопустима.
5. **Метаданные — в заголовках, не в каждой строке.** Сервис, инстанс и релиз одинаковы для всего
   батча; повторять их 500 раз — треть объёма.
6. **Ключи короткие**, потому что их пишут на каждую строку.
7. **Пол семплирования уходит всегда** — даже когда записи запроса отброшены (research §Р7):
   записи `WARN` и выше, ссылки `entity_ref` и счётчики шаблонов. Каждая из трёх держит свой
   сценарий чтения, который иначе ломается молча. **Спаны в пол не входят** и следуют решению
   трассы: один спан на запрос стоил бы ~1,2 ГБ в сутки при 100 rps.
8. **Строка `X-Tracy-Produced` — не то же, что отправленное.** Агент сообщает, сколько байт логов
   он произвёл, а не сколько уехало: «кто шумит» измеряется до семплирования, иначе ответ будет
   про то, сколько мы решили сохранить (research §Р13, Р6).

## Заголовки запроса

| Заголовок | Обяз. | Смысл |
|---|---|---|
| `X-Tracy-Key` | да | ingest-key **инсталляции** (один на установку, не на сервис) |
| `X-Tracy-Service` | да | логическое имя сервиса; незнакомое — заводится само |
| `X-Tracy-Instance` | да | идентификатор инстанса (имя пода + суффикс запуска) |
| `X-Tracy-Release` | нет | версия релиза / тег образа / git sha |
| `X-Tracy-Seq` | да | монотонный номер батча инстанса; дырки = потерянные батчи |
| `X-Tracy-Dropped` | нет | сколько записей дропнуто буфером с прошлого батча |
| `X-Tracy-Produced` | нет | сколько байт логов сервис **произвёл** с прошлого батча (до семплирования) — знаменатель для «кто шумит» |
| `X-Tracy-Sent` | нет | часы агента в момент отправки батча. Без него разница часов **не вычисляется** — см. ниже |

## Запись лога (строка NDJSON, `k` отсутствует)

| Поле | Тип | Смысл |
|---|---|---|
| `t` | Long | время записи, epoch ms, по часам **источника** |
| `n` | Long | монотонный номер записи внутри инстанса — задаёт порядок внутри сервиса независимо от часов |
| `l` | String | уровень: `TRACE`/`DEBUG`/`INFO`/`WARN`/`ERROR` |
| `g` | String | имя логгера |
| `m` | String | сообщение |
| `u` | Int? | `1`, если сообщение интерполировано → **недоверенное** (research §Р8). Отсутствие = `0` |
| `f` | Object? | структурные поля; значения **недоверенные** всегда |
| `tr` | String? | `trace-id`, 32 hex |
| `sp` | String? | `span-id`, 16 hex |
| `e` | Object? | исключение: `{"c":"<класс>","m":"<сообщение>","s":"<стектрейс>"}` |
| `r` | String[]? | имена полей, значения которых были **отредактированы** агентом — чтобы на чтении было видно, что маскировка сработала, а не что поле пустое. Значение `<message>` означает, что редакция сработала по **тексту сообщения**: у секрета в URL имени поля нет (research §1.10) |
| `ix` | String[]? | имена полей, помеченных ключами сущностей (`indexed = true`). Сервер заводит по ним `entity_ref` — [feature-entity-search](../features/feature-entity-search.md). Агент **дедуплицирует** ссылки по `(key, value, trace_id)`: `ix` присутствует у первой записи сущности в трассе, у последующих — нет |

## Счётчик шаблонов (строка NDJSON, `k = "c"`)

| Поле | Тип | Смысл |
|---|---|---|
| `k` | String | `"c"` — дискриминатор |
| `t` | Long | начало минутного окна, epoch ms |
| `m` | String | шаблон сообщения |
| `l` | String | уровень |
| `c` | Int | сколько раз событие произошло **в окне, до семплирования** |

Счётчики отправляются **всегда**, независимо от того, поехали ли тела записей (research §Р13).
Это то, что делает частоту события точной при `sampleRate = 0.01`, а не заниженной в сто раз.

Порог уровня на счётчики действует: подавленное порогом событие не считается.

## Спан (строка NDJSON, `k = "s"`)

| Поле | Тип | Смысл |
|---|---|---|
| `k` | String | `"s"` — дискриминатор |
| `tr` | String | `trace-id`, 32 hex |
| `sp` | String | `span-id` этого спана, 16 hex |
| `pp` | String? | `parent-id`; отсутствует у корневого спана трассы |
| `nm` | String | имя: `POST /orders` для входящего, `GET https://billing/charge` для исходящего, аргумент `withSpan` для ручного |
| `ki` | String | вид: `server` / `client` / `internal` |
| `t` | Long | начало, epoch ms, по часам источника |
| `d` | Int? | длительность в ms. **Отсутствие = спан не закрыт**: сброшен при штатном завершении процесса (SIGTERM). При `SIGKILL` не доедет ничего — тот случай виден только со стороны вызывающего |
| `st` | Int? | статус ответа для `server`/`client` |
| `er` | Int? | `1`, если спан завершился ошибкой |
| `f` | Object? | атрибуты; значения **недоверенные**, как и у записи лога |

Имя спана — **шаблон маршрута**, а не путь запроса: `/users/{id}`, не `/users/42`. Это тот же
урок, что и в metrik (сырой путь взрывает кардинальность); здесь он ещё и держит имя спана
доверенным (research §Р8).

**Поправка после §1.10.** У исходящего спана в первой редакции стояло имя `GET https://billing/charge`
— то есть полный URL. Так нельзя: живой токен, найденный в настоящих логах, лежал именно в пути
URL. Имя спана — низкокардинальная структура, которую читают как доверенную, и это худшее место
для креденшала. Поэтому имя строится как `METHOD scheme://host/path`: **query-строка отбрасывается
целиком** (там живут ключи и по-запросные значения — и утечка, и кардинальность), а к остатку
применяется редакция.

## Ссылка на сущность (строка NDJSON, `k = "r"`)

| Поле | Тип | Смысл |
|---|---|---|
| `k` | String | `"r"` — дискриминатор |
| `tr` | String | `trace-id` трассы, в которой сущность трогали |
| `key` | String | имя ключа сущности |
| `val` | String | значение |
| `t` | Long | время, epoch ms |

Отдельная строка нужна потому, что **ссылка переживает отброшенную трассу, а тело — нет**
(research §Р12). Когда семплирование выбрасывает запись, агент шлёт вместо неё ссылку; сервер
пишет `entity_ref` с `entry_id = null`, и «корзину 12345 трогал orders-api в 14:03 в трассе X»
остаётся видно.

Без этого вида строки сохранить ссылку можно было бы только вместе с целой записью — то есть ровно
той ценой, ради ухода от которой семплирование и существует.

Когда трасса **сохраняется**, отдельные ссылки не шлются: их несёт поле `ix` записи.

## Ответы

| Условие | Статус | Тело |
|---|---|---|
| батч записан | `202` | `{"accepted":<n>,"malformed":<m>,"suppressedKeys":[…]}` |
| неверный или отсутствующий `X-Tracy-Key` | `401` | `{"error":"unauthorized"}` |
| нет обязательного заголовка / тело не NDJSON | `400` | `{"error":"<что именно>"}` |
| батч больше `TRACY_MAX_BATCH_BYTES` | `413` | `{"error":"batch too large"}` |
| БД недоступна или потолок размера не удалось освободить | `503` | `{"error":"unavailable"}` — агент **ретраит** |

Строка, которую не удалось разобрать, **не роняет батч**: она пропускается и считается в
`malformed`; остальные записи сохраняются. Логи — не транзакция.

`accepted` пишется **всегда**, в том числе нулём. Это не стилистика: kotlinx.serialization не
пишет значения по умолчанию, и батч, в котором не разобралась ни одна строка, отвечал бы `{}` —
байт в байт тем же, что и успех. Молчаливый гейт внутри средства наблюдаемости — ровно та
поломка, ради которой оно и заводится.

### Две величины времени, а не одна

`X-Tracy-Sent` появился в 0.2.1 и разделил то, что раньше было одним вычитанием.

| Величина | Как считается | Что означает |
|---|---|---|
| `clock_skew_ms` | `получено − отправлено` | разница часов агента и сервера |
| `record_age_ms` | `отправлено − самая старая запись батча` | задержка доставки: ожидание флаша плюс ретраи |

Раньше писалось `получено − самая старая запись`, то есть **сумма** этих двух. На стенде это
дало 60 966 мс «перекоса часов» у двух сервисов — ровно потолок отката отправителя, и никаких
часов. Поле, заведённое по research риску 6 ради честного порядка событий в трассе с нескольких
подов, сообщало ретрай как расхождение часов.

Второе вычитание целиком идёт по часам агента, поэтому разницы часов в нём нет по построению.

**Без заголовка разница часов считается неизвестной, а не нулевой в смысле «часы сходятся».**
Агент старше 0.2.1 её не присылает, и подставить старую формулу означало бы вернуть ровно то
число, из-за которого всё это и переделано.

### `suppressedKeys` — канал управления, а не информация

Список ключей сущностей, индексирование которых сервер выключил по бюджету (research §Р15).
Агент обязан прекратить эмитировать `ix` по этим ключам — это не совет, а единственное место, где
решение до него доезжает.

Свойства, которые надо реализовать буквально:

* список идёт **в каждом** `202`, а не только в момент изменения: агент, поднявшийся после
  рестарта, получает актуальное состояние первым же ответом;
* поэтому после рестарта один батч ссылок по подавленному ключу всё же уедет. Перелёт ограничен
  одним батчем и принят сознательно: durable-состояние в агенте означало бы запись на диск внутри
  чужого пода;
* пустой список — законное значение и означает «ничего не подавлено», а не «поле забыли».

## Поведение агента при ошибках

| Ответ | Что делает агент |
|---|---|
| `202` | освобождает батч из буфера |
| `401`, `400`, `413` | **не ретраит** — повтор не поможет; считает счётчик, продолжает работу |
| `503`, таймаут, сетевая ошибка | ретрай с экспоненциальной паузой, батч остаётся в буфере; при переполнении дроп с конца |

## Грабли, известные заранее

* **Доменное имя на Kotlin/Native не резолвится** сокетами ktor-network — `connect` падает с
  `EINVAL` (research §1.5, metrik §1.6). Endpoint в кластере — доменное имя, значит резолвить
  самим через `getaddrinfo` на каждое подключение (кеш переживёт переезд пода и будет молчать).
* **`HttpClient(CIO)` на Kotlin/Native не умеет TLS.** Движок на нативных таргетах — curl
  (research §1.5, metrik §1.7). Klib curl несёт статические `libcurl.a`/`libssl.a`/`libcrypto.a`,
  но образу нужны `ca-certificates`.
* **`SelectorManager` отбирает воркер `Dispatchers.Default`** и на 2-ядерном поде ломает `delay`
  во всём процессе (research §Р4). Агент живёт в чужом процессе — это его первое ограничение,
  а не деталь.
